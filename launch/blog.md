# What we learned benchmarking PII redaction for LLM prompts

A privacy proxy for LLM prompts sounds straightforward: find sensitive strings, replace them, send the prompt, and restore originals when the answer returns. The hard part is measurement.

We built VeilRelay as a local, OpenAI-compatible proxy to explore that problem. It scans supported text before forwarding a chat-completion request, replaces detected values with typed placeholders such as `<EMAIL_1>`, and restores known placeholders in ordinary and streamed responses. The mapping stays in memory and is request-scoped by default. Its audit log records entity types and counts, never prompt text or matched values.

The first lesson was to put the threat model at the center of the product. Pattern detection can reduce accidental disclosure of identifiers and common credentials, but it cannot identify every context-dependent secret. A determined user can encode or obfuscate a value. A compromised host can read process memory. The proxy cannot control provider retention or provider-side attacks. We describe it as a risk-reduction layer, not a guarantee that sensitive data cannot leave a machine.

The second lesson was that a regression fixture can tell a misleading story. Our synthetic fixture contains email addresses, Indian-format phone numbers, a checksum-valid Aadhaar-shaped number, PAN, IFSC, UPI, payment/account identifiers, documentation IP addresses, and deliberately fake provider credentials. It is designed to catch implementation mistakes. VeilRelay matched the fixture annotations in the current run. That is useful evidence for those examples, not evidence of high recall on real prompts or an estimate of production false-positive rates.

To make comparison reproducible, the harness matches exact character spans by `(start, end, entity_type)`. A correct value with a different boundary or label counts as a false positive and a false negative. We compare the built-in detector with a deliberately simple regex baseline and Microsoft Presidio's default Analyzer when its optional dependencies are available.

The most important result from the first run is what we could not measure. Presidio did not initialize in the offline environment, so it is recorded as skipped. The public Ai4Privacy OpenPII Nano sample is an optional CC-BY-4.0 input, but it was not downloaded for this run. The Ollama utility harness defines summarization, extraction, and question-answering comparisons, yet no local model was configured, so utility preservation is also skipped. Missing measurements are not converted into zero scores, and no comparison table is invented to make the project look complete.

That utility question deserves attention. Placeholders preserve entity type and repeated identity, so a model may understand that `<PERSON_1>` refers to the same person throughout a prompt. But some tasks depend on literal values. If a model must extract an email address, it needs to echo the token so the proxy can restore it. If it must reason about an account number's format, redaction can remove useful information. Reversible restoration solves the response substitution problem; it does not prove task quality is unchanged. The harness restores placeholders before scoring; local model runs and human evaluation are still needed.

The practical conclusion is modest: start with narrow regression tests, keep false-positive traps, publish raw outputs, and mark missing comparisons as missing. Use checksums where an identifier supports them, but do not confuse a valid checksum with identity verification. Keep fail-closed behavior as the default and raw values out of logs. Do not turn a tiny synthetic score into a security claim.

VeilRelay is an alpha experiment and invites review of its threat model, detection logic, and benchmark design. The next credible milestone is running the public dataset, a clean Presidio comparison, and utility tests against a documented local model setup—then publishing raw results, including failures.
